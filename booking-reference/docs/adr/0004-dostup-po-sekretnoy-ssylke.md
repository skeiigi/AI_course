# ADR 0004. Секрет для доступа к каждой брони

- **Статус:** принято
- **Дата:** 6 октября 2026

## Контекст

В проекте нет учётных записей и рассылки писем. Открытый список броней и отмена
по числовому ID позволяют читать чужие контактные данные и отменять чужие записи.
Проверка одного адреса почты в запросе не доказывает право доступа.

## Решение

Для каждой новой брони создаётся случайный секрет из 32 байт. API возвращает
его только при создании. В таблице `booking_access` сохраняется SHA-256 хеш
секрета, связанный с бронью. Вставка брони и хеша проходит в одной транзакции.

`GET /api/bookings/{booking_id}` и отмена требуют заголовок
`Authorization: Bearer <секрет>`. При отсутствующем или неверном секрете сервис
отвечает `404`, не подтверждая существование брони. Общий список броней удалён.
Ответы с данными и секретом получают `Cache-Control: no-store`.

Ссылка на страницу содержит ID и секрет после `#`. Фрагмент не отправляется
браузером в HTTP-запросе страницы; интерфейс передаёт секрет API в заголовке и
сохраняет ссылки в хранилище браузера. Любой, получивший ссылку, может открыть и
отменить бронь, поэтому интерфейс предупреждает гостя о её секретности.

## Последствия

- Существующие брони в базе сохраняются, но у них нет выданного гостю секрета.
  После проверки владельца локальный оператор может один раз выдать ссылку
  командой `npm run issue:booking-link -- <id> <адрес сайта>`.
- Потерянную ссылку нельзя восстановить по адресу почты. Для восстановления
  потребуется отдельная процедура подтверждения владельца.
- Список всех броней для организатора нельзя публиковать без отдельной
  авторизации; соответствующий сценарий откладывается.
