# ADR 0005. Атомарное групповое бронирование

- **Статус:** принято
- **Дата:** 6 октября 2026

## Контекст

Один запрос может содержать несколько слотов. Между проверкой доступности и
записью другой запрос может занять один из них. Частичный успех заставил бы
гостя разбираться, какие встречи состоялись и какие секреты сохранились.

## Решение

Контракт добавляет `POST /api/bookings/batch`. Сервер проверяет формат, отсутствие
повторов, существование всех слотов, будущее время и текущую занятость. Затем
в одной транзакции SQLite создаёт все брони и хеши отдельных секретов доступа.
Частичный уникальный индекс `uq_active_booking` остаётся последним рубежом при
конкурентных запросах. Если вставка любого элемента не удалась, транзакция
откатывает все записи. Секреты возвращаются только при успешном завершении.

Одиночный эндпоинт сохраняется. Оба пути используют одну проверку правил
бронирования, а существующие данные базы не требуют миграции.
