# AGENTS.md

Файл с правилами работы ИИ-агента в этом репозитории.

Перед внесением изменений в код агент должен полностью прочитать этот файл и ознакомиться с соответствующими частями проекта.

## 1. Что за проект

Сервис бронирования предназначен для поиска услуг, просмотра доступного расписания и оформления бронирований. Пользователь выбирает услугу, дату и время, вводит контактные данные и получает подтверждение бронирования.

Организатор может добавлять услуги, настраивать расписание, просматривать поступившие заявки и управлять ими. Администратор контролирует работу сервиса и пользователей.

Проект разрабатывается в рамках курса «ИИ для разработчиков» (СФУ, Академия Softline).

Основная цель - создать удобный и надёжный веб-сервис, который автоматизирует процесс бронирования и избавляет пользователей от необходимости согласовывать время через переписку и звонки.

При разработке необходимо придерживаться следующих принципов:

* Понятная и логичная архитектура.
* Разделение бизнес-логики, работы с базой данных и интерфейса.
* Надёжная обработка бронирований и предотвращение конфликтов.
* Проверка входных данных на стороне сервера.
* Автоматическое тестирование основных сценариев.
* Отсутствие избыточной сложности и ненужных зависимостей.
* Возможность дальнейшего расширения проекта.

Код должен быть современным, читаемым и удобным для сопровождения. Не следует усложнять реализацию без необходимости или создавать абстракции, которые не решают конкретных задач.

## 2. Стек

| Слой                   | Технология                  |
| ---------------------- | --------------------------- |
| Язык                   | TypeScript в строгом режиме |
| Среда выполнения       | Node.js 22 LTS              |
| Веб-фреймворк          | Fastify 5                   |
| Проверка данных        | Zod 4                       |
| База данных            | SQLite через better-sqlite3 |
| Контракт API           | TypeSpec, OpenAPI 3.1       |
| Интерфейс              | Vite, React 19              |
| Стилизация             | Собственный CSS             |
| Тесты                  | Vitest, Playwright          |
| Контейнеризация        | Docker, Docker Compose      |
| Непрерывная интеграция | GitHub Actions              |

Проект использует npm workspaces. Все зависимости устанавливаются одной командой `npm install` из корня репозитория.

Новые библиотеки и технологии следует подключать только в том случае, если существующих инструментов недостаточно для решения задачи.

## 3. Где что лежит

```text

  main.tsp                 контракт API на TypeSpec
  openapi.yaml             собранный контракт OpenAPI

server/
  src/
    db.ts                  подключение к SQLite и схема таблиц
    repository.ts          SQL-запросы и доступ к данным
    schemas.ts             схемы Zod и типы
    availability.ts        вычисление доступности услуг
    booking.ts             бизнес-логика бронирования
    errors.ts              ошибки и их описания
    routes/
      services.ts          маршруты управления услугами
      bookings.ts          маршруты бронирования
      users.ts             маршруты пользователей
      admin.ts             маршруты администратора
    app.ts                 сборка приложения Fastify
    config.ts              конфигурация приложения
    index.ts               точка входа
    seed.ts                демонстрационные данные
  tests/                   тесты сервера

web/
  src/
    api.ts                 запросы к API и типы ответов
    dates.ts               работа с датами и временем
    hooks.ts               хуки загрузки данных
    App.tsx                корневой компонент
    components/            компоненты интерфейса
    styles.css             стили приложения

e2e/                       сквозные тесты Playwright

docs/
  adr/                     архитектурные решения
  pdr/                     продуктовые решения
```

При изменении проекта необходимо придерживаться существующей структуры. Если возникает необходимость добавить новые файлы или модули, они должны находиться в соответствующих директориях.

## 4. Как запускать

Установка зависимостей из корня проекта:

```bash
npm install
```

Заполнение базы демонстрационными данными:

```bash
npm run seed
```

Запуск сервера:

```bash
npm run dev:server
```

Запуск клиентской части:

```bash
npm run dev:web
```

Интерфейс доступен по адресу `http://localhost:5173`. Запросы к `/api` перенаправляются на сервер через прокси Vite.

Сборка и запуск приложения:

```bash
npm run build
npm start
```

Запуск через Docker Compose:

```bash
docker compose up --build
```

## 5. Как тестировать

Перед завершением задачи необходимо выполнить соответствующие проверки:

```bash
npm run typecheck
npm test
npm run build
npm run e2e
```

* **Модульные тесты** проверяют отдельные функции, в том числе вычисление доступности и правила бронирования.
* **Интеграционные тесты** проверяют работу API, взаимодействие с базой данных и обработку ошибок.
* **Контрактные тесты** проверяют соответствие API спецификации OpenAPI.
* **Сквозные тесты** проверяют основные сценарии через пользовательский интерфейс.

Особое внимание необходимо уделять:

* Созданию бронирований.
* Защите от двойного бронирования.
* Отмене заявок.
* Проверке доступности времени.
* Управлению услугами и расписанием.
* Корректности пользовательских данных.
* Обработке ошибок и конфликтующих запросов.

Если изменение затрагивает определённую функциональность, необходимо добавить или обновить соответствующие тесты.

Не утверждать, что проверки прошли успешно, если они фактически не запускались.

## 6. Порядок работы

При изменении API придерживаться подхода Design First:

1. Изменить `contract/main.tsp`.
2. Пересобрать контракт командой `npm run contract:build`.
3. Обновить схемы Zod в `server/src/schemas.ts`.
4. Изменить бизнес-логику в соответствующих модулях.
5. Обновить обработчики в `server/src/routes/`.
6. Обновить типы и запросы в `web/src/api.ts`.
7. При необходимости изменить компоненты интерфейса.
8. Добавить или обновить тесты.
9. Запустить проверки.

Файл `contract/openapi.yaml` генерируется автоматически. Не редактировать его вручную.

При работе над задачами, не затрагивающими API, не нужно изменять контракт без необходимости.

Перед реализацией новой функциональности необходимо проверить, предусмотрена ли она в PDR. Если изменение затрагивает архитектуру, следует проверить существующие ADR и при необходимости создать новое решение.

## 7. Соглашения по коду

* Комментарии и тексты интерфейса писать на русском языке.
* Имена переменных, функций, типов и файлов писать на английском языке.
* Для переменных и функций использовать `camelCase`.
* Для типов и интерфейсов использовать `PascalCase`.
* Для полей API использовать `snake_case`.
* Использовать строгую типизацию TypeScript.
* Не применять `any` для обхода ошибок типизации без веской причины.
* Типы импортировать через `import type`.
* Комментарии должны объяснять причину принятого решения, а не пересказывать код.
* Функции должны выполнять одну логическую задачу.
* Не создавать избыточные абстракции и сложные конструкции, если задачу можно решить проще.

### Архитектура

* Бизнес-логика должна находиться отдельно от HTTP-обработчиков.
* Все SQL-запросы должны располагаться в `server/src/repository.ts`.
* Проверка входных данных должна выполняться с помощью Zod.
* Маршруты должны отвечать за обработку запросов, вызов бизнес-логики и формирование ответов.
* Логика работы с базой данных не должна находиться в компонентах React.
* Бизнес-правила бронирования не должны дублироваться на клиенте и сервере как независимые реализации.

### Даты и время

* Даты передавать в формате `YYYY-MM-DD`.
* Время передавать в формате `HH:mm:ss`.
* Использовать единый часовой пояс, определённый проектом.
* Преобразование дат и времени централизовать.
* Не допускать зависимости вычислений от локального часового пояса машины.
* При расчёте доступности учитывать продолжительность услуги и пересечения временных интервалов.

### Бронирования

* Доступность выбранного времени обязательно проверять на сервере.
* Защищать создание бронирования от конкурентных запросов.
* Не полагаться только на клиентскую проверку доступности.
* При отмене изменять статус бронирования, а не удалять запись.
* Отменённые бронирования не должны блокировать время.
* Каждое бронирование должно быть связано с существующей услугой.
* Изменение статусов должно выполняться через бизнес-логику сервера.

### Обработка ошибок

* Использовать единый подход к обработке ошибок API.
* Возвращать понятные сообщения на русском языке.
* Для ошибок использовать соответствующие HTTP-коды.
* Ошибки валидации возвращать с кодом `422`.
* Конфликты бронирования возвращать с кодом `409`.
* Использовать машиночитаемые коды ошибок.
* Не раскрывать пользователю внутренние ошибки сервера, SQL-запросы и стек вызовов.

### Интерфейс

* Интерфейс должен быть понятным и адаптивным.
* Основные действия должны быть доступны без лишних переходов.
* Для асинхронных операций отображать состояние загрузки.
* При ошибках показывать пользователю понятные сообщения.
* После создания или отмены бронирования обновлять данные интерфейса.
* Формы должны проверять обязательные поля и корректность введённых данных.
* Для оформления использовать собственный CSS без библиотек компонентов.

## 8. Чего делать нельзя

* Не добавлять зависимости без необходимости.
* Не подключать Tailwind, готовые библиотеки компонентов и библиотеки иконок.
* Не менять выбранный стек без обоснования.
* Не переносить SQL-запросы в обработчики маршрутов.
* Не размещать бизнес-логику в компонентах React.
* Не редактировать `contract/openapi.yaml` вручную.
* Не допускать двойного бронирования одного временного интервала.
* Не удалять записи о бронированиях при отмене.
* Не полагаться только на проверки на стороне клиента.
* Не хранить конфиденциальные данные в открытом виде.
* Не возвращать внутренние ошибки сервера пользователю.
* Не отключать строгую типизацию TypeScript.
* Не использовать `any` для упрощения кода без необходимости.
* Не добавлять функциональность, выходящую за рамки PDR, без согласования.
* Не реализовывать платёжную систему в текущей версии.
* Не добавлять интеграции со сторонними календарями без отдельного решения.
* Не коммитить `booking.db`, `node_modules/`, `dist/` и отчёты Playwright.
* Не усложнять код ради сокращения количества строк.
* Не переписывать работающие модули, если задачу можно решить точечными изменениями.

## 9. Частые задачи

**Добавить новое поле в услугу.**

1. Изменить модель в `contract/main.tsp`.
2. Пересобрать контракт.
3. Обновить схемы Zod в `server/src/schemas.ts`.
4. Добавить поле в схему базы данных в `server/src/db.ts`.
5. Обновить запросы в `server/src/repository.ts`.
6. Обновить бизнес-логику и обработчики.
7. Обновить типы и интерфейс.
8. Добавить тесты и выполнить проверки.

**Добавить новый эндпоинт.**

1. Описать операцию в `contract/main.tsp`.
2. Пересобрать контракт.
3. Создать или дополнить файл в `server/src/routes/`.
4. Добавить бизнес-логику, если она необходима.
5. Добавить SQL-запросы в `server/src/repository.ts`.
6. Подключить маршрут в `server/src/app.ts`.
7. Обновить клиентский API.
8. Добавить тесты.

**Изменить правила доступности.**

1. Проверить существующую реализацию в `server/src/availability.ts`.
2. Внести изменения в логику расчёта.
3. Проверить пересечения временных интервалов и продолжительность услуг.
4. Обновить модульные тесты.
5. Убедиться, что изменения не нарушают процесс бронирования.

**Изменить процесс бронирования.**

1. Проверить, затрагивает ли изменение API.
2. При необходимости обновить контракт.
3. Изменить бизнес-логику в `server/src/booking.ts`.
4. Обновить запросы к базе данных при необходимости.
5. Проверить защиту от двойного бронирования.
6. Обновить обработчики и интерфейс.
7. Добавить тесты для успешных и ошибочных сценариев.

**Добавить новый статус бронирования.**

1. Определить назначение статуса и допустимые переходы.
2. Обновить контракт API.
3. Обновить схемы и типы.
4. Изменить бизнес-логику.
5. Обновить отображение статуса в интерфейсе.
6. Проверить влияние статуса на доступность времени.
7. Добавить тесты.

**Исправить ошибку.**

1. Определить причину ошибки и способ её воспроизведения.
2. Найти модуль, отвечающий за проблемную функциональность.
3. Исправить причину ошибки, а не только её внешнее проявление.
4. Добавить тест, воспроизводящий ошибочную ситуацию.
5. Запустить соответствующие проверки.
6. Убедиться, что исправление не нарушило другие сценарии.

## 10. Правила работы ИИ-агента

* Перед началом задачи изучить этот файл и относящиеся к задаче части проекта.
* Перед изменением кода изучить существующую реализацию и её зависимости.
* Вносить только необходимые изменения, не затрагивая посторонние модули.
* Не переписывать существующую архитектуру без веской причины.
* Если задача противоречит PDR или ADR, сообщить об этом до внесения изменений.
* Если требования неоднозначны и влияют на архитектуру или поведение сервиса, запросить уточнение.
* При реализации новой функциональности учитывать существующие соглашения и структуру проекта.
* После внесения изменений запускать соответствующие тесты и проверки.
* Сообщать о результатах тестирования, включая ошибки и проверки, которые не удалось выполнить.
* При обнаружении дополнительных проблем сообщать о них отдельно, не расширяя задачу самостоятельно.
* Обновлять документацию, если изменения затрагивают архитектуру, API или поведение сервиса.
* Не считать задачу завершённой, если изменения не соответствуют её требованиям.

Основной приоритет - надёжность бронирования, понятность кода, согласованность архитектуры и соответствие требованиям проекта.
