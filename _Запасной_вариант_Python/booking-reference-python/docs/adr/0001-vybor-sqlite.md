# ADR 0001. Хранилище: SQLite через SQLAlchemy 2.x

- **Статус:** принято
- **Дата:** 28 сентября 2026
- **Авторы:** команда курса «ИИ для разработчиков», СФУ

## Контекст

Сервису нужно хранить три сущности: виды активности, расписания и брони.
Объём данных небольшой: десятки активностей, сотни броней.

Проект является эталонным для учебного курса. Его будут запускать 6–14 студентов
на своих ноутбуках, преимущественно под Windows, в аудитории, в пределах одного занятия.
Дополнительные ограничения:

- Занятие ограничено по времени: от 2 до 6 ак. часов. Время на настройку окружения
  нужно свести к минимуму, иначе на саму разработку его не останется.
- Аудитории меняются от занятия к занятию, стабильность сети не гарантирована.
- Docker студенты видят на этом курсе впервые, поэтому сервис должен
  запускаться и без него, одной командой `uvicorn app.main:app --reload`.
- Пакеты с расширениями на C под Windows это отдельная боль: если готового
  колеса для нужной версии Python нет, pip начнёт собирать пакет из исходников,
  понадобятся средства сборки Visual Studio, и занятие уйдёт на их установку.

## Рассмотренные варианты

**PostgreSQL в Docker.** Ближе к промышленной практике и снимает ограничение
на одновременную запись. Отклонено: студенту пришлось бы поднять контейнер
до первой строки кода, а Docker Desktop под Windows у части группы не заработает
с первого раза. Это съело бы занятие целиком.

**Модуль `sqlite3` из стандартной библиотеки, без ORM.** Самый короткий путь:
модуль входит в поставку Python, ставить нечего, SQL виден студенту целиком.
Отклонено: курсор возвращает кортежи, поэтому каждый обработчик начинался бы
с ручной сборки объекта из полей строки, а описание таблиц жило бы в проекте
только в виде текста `CREATE TABLE`. На восьми эндпоинтах это заметный объём
однообразного кода, который отвлекает от темы занятия. Преобразование даты
и времени и поддержание связей между таблицами тоже пришлось бы писать руками.

**Django ORM.** Зрелая ORM с миграциями, готовой админкой и большим
сообществом. Отклонено: она тянет за собой весь Django, то есть настройки
проекта, приложения и `manage.py`. Сервис написан на FastAPI, и подключение
Django ORM в отрыве от фреймворка требует ручной настройки, объяснение которой
заняло бы больше времени, чем вся работа с базой на занятии.

**Tortoise ORM.** Асинхронная ORM, по духу близкая к FastAPI, описание моделей
похоже на Django. Отклонено: обработчики пришлось бы сделать асинхронными,
и в каждом появилось бы по три-четыре `await` на запрос без всякой пользы:
обращения к локальному файлу занимают десятки микросекунд. Кроме того,
библиотека распространена заметно меньше: ответ на свой вопрос по SQLAlchemy
студент находит сразу, по Tortoise ORM реже. Миграции в ней делает отдельный
инструмент aerich, который пришлось бы вводить и объяснять.

**Хранение в JSON-файле.** Не требует ничего. Отклонено: пришлось бы
самостоятельно писать блокировки и проверки целостности, а главное, студенты
не увидели бы ни транзакций, ни уникальных индексов. Защита от двойного
бронирования на уровне базы стала бы невозможной.

**Хранение в памяти процесса.** Самый простой вариант. Отклонено: данные
исчезают при перезапуске, поэтому демонстрация «забронировали, перезапустили,
бронь на месте» не получилась бы.

## Решение

Используем SQLite через SQLAlchemy 2.x. Файл базы `booking.db` создаётся
автоматически при первом запуске в корне проекта. Путь к файлу меняется
переменной окружения `BOOKING_DB_FILE`, этим пользуется `docker-compose.yml`.

Работа с базой разложена по трём местам. Движок, фабрика сессий и базовый класс
моделей лежат в `app/database.py`. Таблицы, типы столбцов и индексы описаны
классами в `app/models.py`. Запросы собраны выражениями SQLAlchemy (`select`)
в роутерах `app/routers/`: обработчик получает сессию из зависимости
`get_session` и работает через неё.

Обработчики остаются синхронными, они объявлены обычным `def`. FastAPI
выполняет такие обработчики в пуле потоков, поэтому асинхронный драйвер
и `await` перед каждым запросом ничего бы не ускорили: обращение к локальному
файлу занимает десятки микросекунд, зато в коде появилось бы по три-четыре
`await` на обработчик.

Проверку внешних ключей SQLite по умолчанию не делает, поэтому она включается
при каждом подключении: `PRAGMA foreign_keys=ON` в `app/database.py`.

## Последствия

**Положительные:**

- Установка сводится к `pip install -r requirements.txt`. Отдельный сервер
  базы данных ставить не нужно, порты настраивать не нужно.
- Модуль `sqlite3` входит в поставку Python, поэтому отдельный драйвер базы
  ставить не нужно вовсе. SQLAlchemy приходит готовым колесом для Windows,
  macOS и Linux, а если колеса для конкретной версии Python не нашлось,
  библиотека работает и без ускоряющего расширения на C. Компилятор
  на машине студента не нужен.
- Проект запускается без интернета, если зависимости уже установлены.
- Тесты работают быстро: каждый тест получает свою пустую базу во временной
  папке, весь набор из 91 теста проходит примерно за 2 секунды.
- Начать с чистого состояния можно удалением одного файла.
- Структура таблицы описана в проекте один раз. Классы в `app/models.py` задают
  и схему базы, и типы полей в коде, поэтому таблица и модель не расходятся,
  а опечатку в имени столбца видит редактор.
- Переход на PostgreSQL потребует замены строки подключения и проверки
  нескольких мест: запросы написаны выражениями SQLAlchemy и от диалекта
  почти не зависят.

**Отрицательные:**

- SQLite плохо переносит одновременную запись из многих процессов. Для учебного
  сервиса с одним процессом uvicorn это не проблема, для промышленной нагрузки
  было бы проблемой.
- Синхронные обработчики FastAPI выполняет в пуле потоков. Пул ограничен
  по размеру, поэтому запросы на десятки миллисекунд занимали бы в нём места.
  Здесь запросы короткие.
- Своих типов для даты и времени в SQLite нет: значения хранятся строками
  «ГГГГ-ММ-ДД» и «ЧЧ:ММ:СС», а типы `Date` и `Time` из SQLAlchemy переводят
  их в объекты Python и обратно. Формат выбран так, что строки сравниваются
  и сортируются как сами моменты времени. Часовой пояс SQLite не хранит,
  поэтому время создания брони записывается в UTC без сдвига, смотри функцию
  `now_utc` в `app/models.py`.
- Частичный уникальный индекс задаётся параметром `sqlite_where`, то есть код
  в этом месте привязан к SQLite. В PostgreSQL параметр называется
  `postgresql_where`, а в MySQL до версии 8.0 частичных индексов нет вовсе.
  Смотри ADR 0003.
- Миграций в проекте нет. При изменении структуры таблиц базу нужно удалить
  и наполнить заново. Для учебного проекта это приемлемо.
- SQLAlchemy добавляет между кодом и базой свой слой. Чтобы понять, какой SQL
  уйдёт в SQLite, нужно представлять, во что превращается выражение `select`.
  Это плата за то, что запросы не собираются склейкой строк.
